## Context

Ticket 签发、WebSocket 兑票、新发送和历史查询经 `RoomService.exists()` 调用 MySQL 点查。房间创建已在独立事务内插入并回读，读详情时另取当前房主显示名。本轮沿用这些边界，为存在性点查引入共享缓存。 [变更动机](proposal.md#why) · [缓存存储设计](../../../../docs/design/room/storage.md) · [部署与运行设计](../../../../docs/design/room/deployment-and-operations.md)

## Goals / Non-Goals

**Goals**

- 为同一环境的所有实例复用房间存在结果，控制单 Key 过期、批量冷查与缓存故障时的实际 MySQL 查询量。
- 保证已提交的创建结果和缓存更新各自按实际结果生效，防止旧查询在缓存预热后写回不存在。
- 保留鉴权顺序、已有提交回执和历史快照契约，复用现有 HTTP 与 WebSocket 错误。

**Non-Goals**

- 房间详情、搜索结果、用户资料、回执和历史快照各自遵循原读取路径。
- 房间编辑和删除、Redis 分片、MySQL 迁移和页面改动属于其他变更。

## Decisions

### 1. 存储隔离与模块边界

应用的房间存在性入口统一负责查房、回填、降级和创建后预热。依赖方向沿用 `core` 业务规则与端口、`infrastructure` Redis 适配、`api` 配置和协议映射的结构。物理查库继续走 `RoomMapper.exists()` 和 `uk_rooms_room_uuid`，缓存的正负结果只作为房间存在性判断。

使用独立的 Redis 实例及客户端连接。为缓存配置命令超时并约束断线期间的排队，本机入口就绪保持现有判断。将缓存写入业务 Redis 会共享内存和淘汰策略，独立部署可以按缓存特征选淘汰策略，并能在不停止认证会话、发送冷却或广播的条件下验证回源。配置和 Compose 从既有镜像及部署方式扩展。 [存储归属](../../../../docs/design/room/storage.md#范围与数据归属) · [配置与生效](../../../../docs/design/room/deployment-and-operations.md#配置与生效)

### 2. 共享结果和按房间回填

同一 UUID 的数据键与租约键使用同一哈希标签。结果区分存在、不存在和未命中。使用随机 TTL 分散不同房间的到期，只有 MySQL 明确查无房间才写入较短的负缓存。读命中时保留原截止。

普通命中一次读取即可返回。未命中时，本机合并同 UUID 的在途回填，执行者通过 Lua 重新检查结果并尝试取得带唯一令牌的短租约。持有者受回源预算约束，查库结束后在同一个 Lua 操作中校验所有权、写值并释放。跨实例等待者用抖动间隔复查，全部等待和命令耗时计入同一预算，超时以暂不可用结束。租约到期、被淘汰或被预热清除后，旧持有者无法写值或释放新租约。 [Key 与回填细则](../../../../docs/design/room/storage.md#key-和生命周期)

### 3. 划定回源的速率、并发和错误语义

在申请 MySQL 连接前使用每实例令牌桶和并发许可。未命中、缓存故障、旁路和恢复期间共用一份预算。没有额度时立即拒绝。仅在实际查询结束或确认取消后归还在途许可，即使上层请求先结束仍应计入在途。缓存连接访问失败时，同一实例内只合并当前正在处理的同 UUID 请求，完成后移除在途记录。缓存可用时已经进入等待的请求在当次结束，不另行查库。

单实例预算按实际数据库承载力设定，再将实例预算相加计算部署总量。首轮采用既有设计的每实例 30 次/秒、突发 6、4 条在途，分别观察连接池等待和 SQL 耗时。在相同的总流量下，单加速率限制对容易阻塞的查询缺少并发约束，单加并发限制又可能在 SQL 很快时放任大量冷 UUID 查询。两种额度一起约束当前读路径。 [预算与基线](../../../../docs/design/room/storage.md#缓存故障与回源预算)

物理查库失败仍按 MySQL 依赖失败报告。预算拒绝和等待超时是本地保护，发送归还断路器许可并跳过统计，预约、冷却和生产调用均留在房间检查之后。同一提交先按原逻辑判断已有预约。WebSocket 先消耗 Ticket、复查会话，再检查绑定房间，依赖失败使用服务端错误关闭。使用现有回执 Redis 和历史读快照。 [弹幕接口错误约定](../../../../docs/design/room-messages/v2/api.md#房间存在性判定)

### 4. 在提交后预热，约束负结果的陈旧窗口

创建路径从数据库事务取得确认成功后，才尝试为最终 UUID 预热。Lua 先写正结果，再清除该 UUID 的回填租约，使提交前开始的旧回填失去写入资格。预热一次失败只记录指标和日志，接口仍返回已提交的房间。事务失败或结果未确认时继续用本人查询确认。

负缓存使用 Redis 租约开始时间计算绝对截止。写入时若已经到达该截止，只释放租约。这样即使创建预热失败，提交前开始的旧查询也无法通过晚回填把陈旧窗口延长到当次负 TTL 上限之外。普通删除缓存只能令下一次读取重新查询，单独删除还无法使旧持有者失去写入资格。 [提交与可见性规则](../../../../docs/design/room/storage.md#创建预热和可见性)

## Risks / Trade-offs

- 缓存自身不可用或同一 Key 租约被淘汰 → 健康时保持一次跨实例回填。故障时允许不同实例分别回源，各自执行同一保护预算，并区分缓存异常、回源拒绝与 SQL 错误。
- 持有者在等待预算内无法完成 → 跟随请求按时结束，下一轮等租约到期后可接手。对比正常和人为阻塞场景的 `503`、SQL 次数和延迟。
- 预热失败时读到原负缓存 → 创建响应以 MySQL 为准，限定负结果的绝对截止。本人查询和详情保留直接读取已提交结果。
- 历史查询仍有其他 SQL、发送仍要读取资料 → 压测按查询形状拆分房间存在性、资料、历史阻断、水位和消息页，分别对照基线。

## Migration Plan

先提供独立缓存 Redis，并逐台发布支持受控回源的新版本，默认走旁路。三台都具备保护后逐台打开缓存，冷数据按需回填。缓存故障时确认业务 Redis 继续提供服务，再检查实际回源速率和在途数。回退缓存时先逐台切回旁路并保留回源预算。若退回不含预算的旧制品，按 MySQL 余量控制入口流量。 [发布与回退](../../../../docs/design/room/deployment-and-operations.md#发布与回退)
