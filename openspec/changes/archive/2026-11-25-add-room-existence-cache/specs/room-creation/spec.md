## MODIFIED Requirements

### Requirement: 登录用户创建本人房间

系统 MUST 提供 `POST /api/v1/rooms`，要求有效 Bearer 会话和 CSRF，按认证账号创建房间。请求 MUST 为只含字符串 `title` 的 JSON 对象。名称先拒绝 C0、C1 控制字符及 Unicode 行段分隔符，再按 Unicode White_Space 去除首尾空白，结果 MUST 为 1–40 个 Unicode 码点，保留内部空白与大小写。提交成功 MUST 返回 `201`、`Cache-Control: no-store` 以及房间对象，其中 `roomId` 为标准小写随机 UUID v4，保存后保持稳定，`createdAt` 为带三位小数秒的 UTC ISO 8601 字符串，`title` 为规范化后的名称。

启用共享房间存在性缓存后，系统 MUST 在房间事务确认提交后更新该 UUID 的可见结果。成功更新后，先于该事务确认的不存在结果 MUST 无法重新覆盖已存在结果。缓存更新失败时 MUST 继续以已提交的房间返回 `201`，旧的不存在结果 MUST 在创建提交后不超过配置的负缓存 TTL 上限内失效。事务回滚或提交结果未确认时，创建路径 MUST 保持缓存中无该事务产生的存在结果。

#### Scenario: 创建成功

- **WHEN** 当前账号没有房间，用户携带有效会话及 CSRF 提交合法名称
- **THEN** 系统返回 `201` 和已创建的房间，后续本人查询返回相同房间

#### Scenario: 拒绝无效创建请求

- **WHEN** 请求缺少必填字段、包含额外字段、字段类型错误、JSON 无效或名称不符合规则
- **THEN** 接口返回 `400 INVALID_REQUEST`，且请求没有创建房间

#### Scenario: 拒绝无效凭证

- **WHEN** 写请求的 Bearer 或当前会话无效，或认证用户的请求未通过 CSRF
- **THEN** 系统按现有契约返回对应的认证或 CSRF 错误，且请求没有创建房间

#### Scenario: 创建后旧的不存在结果晚到

- **WHEN** 一个实例已确认房间不存在、尚未发布结果，另一个实例提交该 UUID 对应的房间并成功更新缓存
- **THEN** 后续查房以存在为准，晚到的不存在结果无法使该房间重新不可见

#### Scenario: 创建已提交但缓存不可用

- **WHEN** 房间写入已经提交，但无法写入共享缓存
- **THEN** 创建仍返回 `201` 和已持久化的 UUID，本人查询或详情可取得该房间，旧的不存在结果在负缓存 TTL 上限内失效

#### Scenario: 创建回滚或提交未知

- **WHEN** 创建事务回滚或提交结果无法确认
- **THEN** 创建路径不会提前发布存在结果，后续查询按已提交数据确认实际结果
