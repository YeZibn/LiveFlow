## Context

本方案承接 [弹幕 V2 主设计](../../../docs/design/room-messages/v2/design.md) 和 [三实例部署](../../../docs/design/room-messages/v2/deployment-and-operations.md#三实例部署)。现有实现通过本地 Streams 状态及全部六个分区的本机归属控制发送，通过本机输出消费者的就绪状态控制回执和历史。历史冲突与位点越界也各有进程内记录。部署三份后，每台只处理分到的部分分区，HTTP 路由必须独立于后台任务归属。

## Goals / Non-Goals

**Goals**

- 任意健康实例承接 HTTP 和 WebSocket。Kafka 维护分区归属并在单进程退出后接管。三份应用保持既有房间顺序、账号冷却、单次提交、回执查询和历史补拉。
- 把临时交接和持久阻断送到正确的处理路径，使故障只影响对应职责和范围。
- 沿用 Java 21、Spring MVC、现有 Maven 模块与 Vue。单实例仍可用于本地启动。

**Non-Goals**

- 接入与后台独立部署、Kafka 扩分区、Redis Cluster、MySQL 分库分表和共享依赖高可用属于后续变更。
- 接口和事件沿用现有字段、业务时限、Topic 名、Streams 应用 ID 和各职责 Group ID。

## Decisions

### 1. 同制品和共享数据

同一 JAR 启动三个对等进程，分别配置 `LIVEFLOW_INSTANCE_ID`、端口和独立 Streams 状态目录。三个进程使用相同的成员清单 `LIVEFLOW_CLUSTER_MEMBER_IDS`、JWT 签名配置、Kafka 命名空间、Redis 环境和 MySQL。单实例启动默认使用一个成员；多实例启动校验本机在清单中，清单成员唯一。同一实例标识的替代进程在旧进程退出后启动。

同源代理分配请求和握手；Ticket 通过既有 Redis 单次兑换，WebSocket 建立后由上游实例持有。Kafka 决定后台分工。按房间固定路由会增加会话切换和节点接管的协调成本，对等部署复用当前共享状态处理跨实例请求。连接资源、出站队列和熔断属于本机，认证限流及账号发送冷却属于整个环境。

### 2. 发送按目标分区接入

- 入口从与 Producer 一致的房间 UUID 分区算法取得提交分区。保留既有熔断入口、身份与字段检查、已有预约回查。新提交在 Redis `claim` 前检查目标分区及生产可用性。拒绝释放本机许可，跳过熔断统计，且保留已有绑定、冷却及回执语义。
- 各实例周期写自身运行快照，接入层合并成员快照并周期同步 MySQL 的持久阻断。快照包含启动标识、原采集时间、已恢复任务的分区、交接状态和处理进度。缓存保留采集时间，读取或刷新失败均不得续延已知就绪。仅可用已确认且近期处理的分区在有限宽限内短时排队，冷启动未知分区或长期失去处理能力的分区拒绝新预约。房间分片对应的持久阻断优先，持久视图过期时暂停新预约。
- 积压保护观察目标分区的最老待处理提交年龄。快照明确区分未知和确认无积压，并保证恢复预算早于既有 12 分钟正式接收期限。周期采集与有界缓存约束 Kafka、Redis 和 MySQL 的额外开销。普通部署只需共享检查结果，Kafka 仍是任务归属和事务确认的权威。
- 通过检查后按原路径取得预约并发送一次。Broker 确认是 `202` 的依据，结果不明时保留已知预约的只读查询。发送端继续维护本机生产并发上限。单纯放开生产将使长期停用分区持续累积提交，按分区预检可把拒绝限制到相应房间。

### 3. 读取和持久阻断各按数据来源工作

回执在认证通过后直接从共享 Redis 读取。历史读取与 WebSocket 水位通知使用共享 MySQL。历史查询在同一快照读取水位、消息与目标房间影响范围的历史阻断。普通交接和落库滞后允许读取已提交水位。让查询绕行到分区持有者会让已落库的数据在接管期间也失去可读性。

使用新增 Flyway 迁移创建 [处理阻断表](../../../docs/design/room-messages/v2/database.md#处理阻断记录)。按职责、Topic、分区及可选房间区分作用域，保存明确的错误、位置、报告者及版本。历史批次回滚后，通过独立事务记录阻断；记录写失败时本地保持暂停并告警。接任方先读取共享阻断，再处理分区；暂时无法核对时保持该分区暂停。按原位点重放并保留各职责原有的副作用确认点。修复后按已核验版本解除阻断，读请求和后台处理按各自作用域恢复。临时依赖波动与正常积压由快照、指标和既有退避处理。

Streams 未捕获异常使用 `SHUTDOWN_CLIENT` 限制故障范围。任务由其余实例接管。可定位的持久错误保留故障位置，重复故障需要关联分区和证据后进入修复。现有 `SHUTDOWN_APPLICATION` 的全应用关闭只适合主动停掉整个处理应用的情形。 [Kafka Streams 异常处理](https://kafka.apache.org/documentation/streams/developer-guide/running-app/#uncaught-exception-handler)

### 4. 定时作业和连接恢复

回执恢复和历史清理使用各自的环境级 Redis 租约。值使用每次执行的唯一身份，续租与释放做原子归属校验。回执回放完成时在同一个 Lua 操作中核对租约并更新恢复标记；丢失租约后停止开启后续批次。历史清理仍以 MySQL 事务保证裁剪和水位一致。由三个进程竞争租约，使上一持有者退出后其余进程可接任。实时水位通知继续本机运行，面向本机连接。

入口就绪表达本机可接新流量，分区错误由接口按职责处理。代理覆盖外部转发头，认证限流使用可信来源地址，WebSocket 由代理透传 Upgrade，弹幕 POST 关闭代理重试。计划下线先摘流，处理在途请求后关闭本机 WebSocket 和 Kafka 客户端。Vue 为既有有限重连退避引入抖动，每次重新申请 Ticket，保留当前会话和房间的连续游标。连接恢复只执行接收和补拉。

## Risks / Trade-offs

- 快照可能过时或重启后残留 → 结合实例启动标识、采集时间和短期有效期，明确启动未知与正常交接，持久阻断优先。
- Kafka 交接可能重放已发生的外部副作用 → 保留原 offset 确认边界，MySQL 校验不可变事件与水位，回执幂等投影，浏览器按序号和消息 ID 合并。
- 一台故障后重连流量集中在余下实例 → 前端抖动、接入与待鉴权上限、独立记录重连压力，并用两台存活容量设定常态预算。
- 应用扩容同时增加 Redis 会话复查与 MySQL 水位查询 → 分别观测依赖延迟和批读开销；对单房间、多房间和不同分区分布单独压测。

## Migration Plan

1. 单独应用增量 Flyway 迁移，预建或核对已有 Topic。使用原 Streams 应用 ID、消费组、changelog、offset 和状态目录约定启动新版单实例，完成基本读写与恢复回归。
2. 确认旧版已退出共享 Kafka 应用，再以相同制品和依赖配置加入另外两台。待各分区可用并核对历史与回执推进后接入全部上游。
3. 日常发布依次摘流、等待在途预算、关闭连接、退出消费组、部署新进程，再通过就绪和接管检查后回流。
4. 回退旧单实例版本前先摘除两台，核对相关提交的终态与历史水位，退出两个消费成员后切回单实例。保留 Topic、offset、数据和增量表，仍有持久阻断时先明确修复或停用影响范围。 [发布与回退](../../../docs/design/room-messages/v2/deployment-and-operations.md#发布与回退)

## Open Questions

- 运行快照采集周期、有效期、交接宽限和积压保护阈值由掉一台与滚动发布的演练确定。实现任务应提供可配置的联调起点，记录故障收敛结果后再定部署值。
