## Context

弹幕发送经 MVC 入队，Kafka Streams 正式接收后向广播组和历史组提供同一正式事件。广播组经 Redis Pub/Sub 向各实例推送，历史组批量持久化到 MySQL。现有历史写入把连续序号当作提交条件，Vue 也等待连续序号后才更新列表。业务动机见 [提案](proposal.md)，可观察行为以 [差异规格](specs/room-messages/spec.md) 为准。

## Goals / Non-Goals

- **目标**：让历史允许稀疏写入和迟到补写，将单条确定冲突限制在当前事件。保留批量事务、唯一键裁决及 Kafka 确认边界。浏览器实时展示独立于历史查询。
- **范围边界**：沿用现有发送、正式序号分配、投影回执、Ticket、账号冷却、熔断、三实例拓扑及 Redis 广播。历史恢复使用最近窗口、现有分区阻断表与日志诊断。

## Decisions

### 历史批次与 Kafka 确认

由 `RoomKafkaConsumer` 和历史服务交接已验证的正式事件及原记录 offset。同一分区按 offset 先后裁决，继续用一批一个 MySQL 事务。保留消费者提供的下一位点用于最终确认，它可能跨过 Kafka 事务标记。每条事件的自身 offset 用于冲突日志。

1. 同批只计算一次 UTC 保留截止。对有效候选按房间 UUID 固定顺序创建或锁定状态行，批量从两个唯一键读已有记录。事务内分别维护房间序号与消息 ID 两份已接受记录索引。
2. 两键都空闲时接受事件。房间、序号、消息 ID、账号、显示名快照、正文与受理时间全部一致时确认幂等。任一键命中不同记录时保留已有值，跳过本条。数据库既有记录先裁决，批内只在两键都空闲时按 offset 先后占用。
3. 普通批量插入通过裁决的记录，以本批真实插入的最大序号推进每间房的状态。发生唯一键竞争时回滚本批，在新的事务中重新读取两键并重新裁决。重读能定位到同一记录或具体冲突时按正常分支处理。未知异常、持续写入失败或提交结果不明时沿用分区退避重读，保留 Broker 已提交位置。
4. MySQL 确认提交后才能提交 Kafka 下一位点，即使本批全部过期或已做幂等裁决。MySQL 已提交而 Kafka 确认失败时，重读由同一套规则收敛。

继续批量处理以保留现有吞吐特征。逐条事务会增加提交开销，通用忽略插入会模糊数据库异常与可跳过冲突。冲突记录包含组、Topic、分区、原 offset、房间、序号和来件及命中记录的消息 ID。计数标签只使用有界维度，日志不记录正文或凭证。 [数据库事务](../../../../docs/design/room-messages/v2/database.md#历史写入和水位) · [Kafka 契约](../../../../docs/design/room-messages/v2/event-contract.md#三个输出消费组)

### 最大落库序号与保留

Flyway 将 `room_message_history_state.stored_through` 就地改名为 `latest_stored_seq`，移除 `earliest_seq`，同步替换受影响的检查约束与默认值。历史消息主键和消息 ID 唯一键保留，并将清理索引切到 `(sent_at, room_id, room_seq)`。清理租约继续使用每环境一个持有者。按索引顺序每批最多删除 500 行，删除只作用于消息表。

查询、落库和清理使用同一保留规则，分别在一次请求、写入批次或清理执行内固定 UTC 截止。消息按 `sent_at` 过期，保留 `stored_at` 用于观察延迟。时间裁剪能处理序号无连续前缀的旧消息，并避免按最大序号误删仍在窗口内的较小序号。最大落库序号读自房间状态，供分页上界和进度通知共用。 [目标 DDL 和清理契约](../../../../docs/design/room-messages/v2/database.md)

### 查询、进度通知与阻断

在同一 MySQL 一致性快照中读取历史阻断、房间最大已写序号与消息页，历史表查询走房间及序号范围。最近模式倒序限量后反转。范围模式多读一行决定游标，客户端可沿用响应上限读取后续页。该上限限定序号，先前已经读过的范围需要重新查询才能看到进一步迟到的记录。

`RoomHistoryProtection` 和 `RoomProcessingBlocks` 保留真正的历史分区故障保护。移除新写入路径中的房间冲突登记和对应暂停分支。持久分区阻断在历史 GET 与批量历史进度上应用相同范围。旧冲突记录由协调发布逐条核验和清除。历史进度按连接记忆已入队的最大值，MySQL 读取和 WebSocket 实时写入各自执行。Redis 订阅恢复继续发送原控制帧。 [接口设计](../../../../docs/design/room-messages/v2/api.md#查询历史) · [频道与进度通知](../../../../docs/design/room-messages/v2/storage.md#房间频道与订阅)

### Vue 最近窗口合并

`roomMessagesClient.ts` 接收新的历史字段和进度帧。房间页维护按序号排序的 100 条列表、消息 ID 与序号索引，以及当前连接的历史查询状态。实时帧、最近历史和历史纠正共用合并规则，区分来源以确保后来的冲突实时帧不会盖掉已经确认的历史项。添加迟到项或替换冲突项后按序号排序并裁剪。

以房间、会话和连接代次约束请求及响应，合并同时到来的恢复提示。首次、重连与订阅恢复查询最近窗口。最大落库序号超过实际已见序号时也触发刷新。恢复 GET 有界退避，页面继续显示实时内容。使用最近窗口能保持每次恢复的数据量有界，并允许已经读过的较小序号在窗口内补入。 [客户端合并规则](../../../../docs/design/room-messages/v2/api.md#前端合并与恢复)

## Risks / Trade-offs

- **最大值不能表示无缺口** → 使用 Kafka 分区位点、积压年龄和落库延迟观察历史处理。页面只显示已经获取的记录。
- **较小序号落库不会触发最大值通知** → 通过对应实时帧或下次最近窗口刷新发现。超出窗口的缺失项不影响当前房间列表。
- **跨分区消息 ID 竞争或事务确认丢失** → 依赖数据库唯一键与重读裁决。失败时保留消费位置，诊断计数可能随 Kafka 重放重复出现。
- **延迟写入的消息可更早过期** → 按正式受理时间统一过滤与清理，切换时保留原记录，再按新时间边界清理。
- **全局唯一键的校验依赖留存的历史行** → 正常重放携带原受理时间，过期后直接跳过。数据库清理后也不保存额外历史冲突索引。
- **前后端协议与数据库字段需同步升级** → 使用协调切换，清理旧连接，刷新 Vue 页面。旧版本退出后才迁移表。

## Migration Plan

1. 暂停弹幕入口，记录各历史分区已提交 offset、日志起点、阻断记录和数据库快照位置。等三台旧历史消费者及清理任务退出，以退出后的 Kafka 已提交位置为基线。
2. 执行追加 Flyway 迁移，核对历史行、状态数值、约束和清理索引。使用相同 Kafka 和 Redis 配置启动新后端，通过原消费组接续。
3. 新版接管后逐条检查旧 `HISTORY_SEQUENCE_CONFLICT`，核对历史消费组、Topic、分区、房间、`revision`、可重放位置和已存在记录。确认可重放时按完整主键与版本清除对应记录，依原位点恢复。位点越界按分区故障处理，其余持久阻断保留。
4. 核对同分区两间房推进、历史分页和 WebSocket 通知，再发布配套 Vue 并开放流量。迁移前可以恢复原版流量。迁移后优先用支持新结构和稀疏语义的版本修复。 [协调切换与恢复](../../../../docs/design/room-messages/v2/deployment-and-operations.md#历史容错版本切换)
