## Context

LiveFlow 以一个 Spring Boot 进程提供认证、弹幕发送和 WebSocket 接入。当前认证限流挂在会话仓储上，弹幕在一个 Redis 脚本中处理账号额度、预约和租约。设计以[现有模块分层及限流方案](../../../docs/design/resilience/design.md)为准。

## Goals / Non-Goals

**Goals**

- 在现有三个 Maven 子模块内拆出可独立验证的限流职责，保留认证窗口语义与弹幕确认边界。
- 统一配置和有限维度的观测，按实际剩余时间返回等待提示。
- 按环境清理旧弹幕额度数据，确保既有发送凭据和历史数据仍可用。

**Non-Goals**

- 熔断、并发隔离、多实例部署和独立网关归入后续阶段。
- 本变更沿用现有 MySQL 表和索引、Kafka 事件和房间序号契约。

## Decisions

### 认证规则归属限流模块

在 `liveflow-core` 定义认证限流端口，`liveflow-infrastructure` 提供 Redis 实现，`AuthService` 在现有计数点调用。会话接口只负责会话生命周期。显式接入可以在执行密码计算前取得准确的账号和来源信息；统一 HTTP 拦截器难以对齐业务字段校验和既有扣额时机。

登录 Lua 保留两个同槽的现有 Key，先读取并确认两个状态和 TTL，再共同扣额。只在对应键首次计数时设置到期。任一维度已满时返回最大剩余 TTL，两个维度都保持原状态。注册沿用独立固定窗口脚本与同样的结构化结果语义。应用统一把有效等待时间转成整数秒，并区分限流拒绝与依赖失败。 [认证与弹幕存储定义](../../../docs/design/resilience/storage.md)

### 弹幕冷却和预约共用一次 Lua 执行

新冷却字符串键以账号 ID 为作用域，和预约键共用账号哈希标签。把旧 ZSET 的上限设为 1 也能表达严格间隔，字符串 TTL 则直接表达该规则，避免继续维护多条历史时间戳和旧配置。脚本首先裁决原预约、正文冲突、重试期限和租约；新候选无有效冷却时，以同一次 Redis 时间计算预约许可时刻和冷却截止，再写入两个键。用同一 Redis 时钟与冷却键的绝对截止比较，当前毫秒等于截止时即可放行。冷却有效时等待提示取至少 1 秒。

已确认入队的重试继续走快速路径；Kafka 开始生产和响应结果未知的边界保持既有语义。脚本在写入前验证关键参数与状态。Redis 命令异常时返回依赖失败，Lua 的执行隔离不提供运行错误后的自动回滚；无法确认时沿用已有预约和幂等判决。冷却从获准预约时开始，拒绝和重试都不刷新。 [目标接口](../../../docs/design/resilience/api.md)

### 配置和前端

按[配置表](../../../docs/design/resilience/deployment-and-operations.md#配置)统一绑定正整数配置，继续支持现有注册环境变量。Vue 复用 API 请求层的 `retryAfterSeconds`。登录对有效等待时间提供反馈。弹幕按响应建立本地截止，保留草稿与现有回执和原标识重试，房间离开或会话切换时清理页面计时。服务端仍按账号裁决，包括跨房间重新进入与多标签页请求。指标使用固定策略与结果标签，覆盖允许、超限、依赖失败及耗时。

## Risks / Trade-offs

- 固定窗口边界允许相邻窗口的请求集中通过。首轮沿用已有窗口和数据语义。
- Kafka 异步处理可能让两条消息的展示接近；冷却约束的是 Redis 新预约获准时间。
- 保持原发送顺序时，资料读取发生在新预约裁决之前。限流主要约束已获准提交数。
- 过去按每账号 10 秒 5 条测得的容量基线保留原口径。再次测试新规则时，按每账号 10 秒最多一次分配发送账号。

## Migration Plan

按[发布与旧额度清理](../../../docs/design/resilience/deployment-and-operations.md#发布与旧额度清理)暂停旧发送、确认环境 Redis 和前缀、删除精确匹配的旧弹幕额度 ZSET，再启用新版。清理只在明确选择的环境执行，发布前预览过滤结果。已有认证窗口、预约、回执、MySQL 历史和 Kafka 状态沿用。回退时先停新版发送，旧规则从空额度窗口重新累计，并继续使用相同的业务数据。
