## 验证记录

- 后端在独立 Compose 项目中与 MySQL 8.4.13、Redis 8.2.11 和 Kafka 4.3.2 联调，Maven 执行 33 项测试，全部通过。依赖树中的 Kafka Streams 与 Kafka 客户端均为 4.2.2。
- MySQL 空库应用 V1 至 V9。另建 V8 库写入一间既有房间后升级 V9，原房间仍可读取，并核对了历史表主键、消息唯一键和清理索引。
- 暂停隔离 Broker 后提交返回 `503 MESSAGE_SUBMISSION_UNKNOWN`。Broker 恢复后沿用原标识重试，只产生一条新历史，房间序号到 2。
- 在浏览器中丢弃最后一条实时弹幕，客户端依据历史水位补回。在第一次 POST 已取得 202 后丢弃 HTTP 响应，手动重试使用同一标识，刷新后的四条历史各展示一次。另验证了 Redis 订阅连接断开后的 `resync_required`。
- 暂停 V2 接入返回 503，回退 V1 发送返回 200。仅在测试命名空间回拨历史消费组位点，V2 从新的本机状态目录恢复后，原房间水位从 4 连续增至 5，已落库历史保持幂等。回放已超出实时窗口的广播事件时只下发恢复后的新消息。
- Vue 生产构建、OpenSpec 严格校验及差异空白检查均通过。

### 单实例容量基线

macOS 15.7.4，10 核、16 GiB，Docker 虚拟机 10 核、约 7.65 GiB。Java 21 单进程，单 Kafka Broker。每个场景均从 512 条有效连接提升至 1,000 条，并按目标频率发送约 12 秒。普通场景使用 260 个有效发送账号，观众均分到 10 个房间。热点场景的 1,000 条连接均加入同一房间。

| 场景 | 目标发送速率 | 发起 / 202 / 正式消息 | WebSocket 交付 | 异常关闭 |
| --- | ---: | ---: | ---: | ---: |
| 10 个普通房间 | 100 条/秒 | 1,200 / 1,200 / 1,200 | 120,000 | 0 |
| 单个热点房间 | 20 条/秒 | 240 / 240 / 240 | 240,000 | 0 |

下表为 P50 / P95 / P99，单位毫秒。“正式裁决”自 Redis 首次许可起算，HTTP 全程由客户端测量，其余内部阶段使用应用计时器。热点场景在普通场景的计时分位窗口过期后单独复测。
