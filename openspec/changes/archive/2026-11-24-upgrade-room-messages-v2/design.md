## Context

当前后端的 `RoomMessageController` 在同一次请求中调用 `RoomMessageService` 完成内存去重和广播。Redis 已用于认证和 Ticket，Kafka 已有 Compose 配置与健康检查。Vue 目前由 HTTP `200` 清理发送状态，并按 WebSocket 到达顺序显示。本变更沿用父 POM、Maven 子模块及 Spring MVC。背景见 [提案](proposal.md)，对外语义见 [增量规格](specs/room-messages/spec.md)。

## Goals / Non-Goals

**Goals**

- 将入队、正式接收、持久化历史和实时转发分别放在可确认的边界上。
- 测量并隔离单实例中的 Kafka 生产等待、房间扇出、慢连接与历史批写。
- 延续当前登录和 Ticket 规则，支持断线后的连续游标恢复。

**Non-Goals**

- 首轮部署单个 LiveFlow 进程。业务事件支持后续多实例演进，部署扩容、画面滚动弹幕、在线人数和实时采样留待后续阶段。

## Decisions

### 分层与生产确认

`liveflow-api` 负责现有安全链、MVC DTO、两个新增 GET 的显式授权，以及 WebSocket 协议和客户端控制帧。`liveflow-core` 定义提交、判重、历史、回执的领域职责和接口，保留 MyBatis、Flyway 数据库路径。`liveflow-infrastructure` 实现 Redis 脚本、Kafka Producer、Streams 拓扑和消费适配。Kafka 与 Redis 客户端对象留在基础设施层。新增 Kafka Streams 依赖沿用现有父 POM 的版本管理，先核对项目实际依赖与本地 Broker 的事务配置。 [模块设计](../../../docs/design/room-messages/v2/design.md)

首次发送从可信 JWT 取账号和会话，完成房间、正文和显示名校验。已确认相同预约从 Redis 直接返回原入队回执，读取资料期间的竞争由第二次原子判断裁决。Lua 以同账号同槽键原子登记额度、正文摘要、显示名与发送租约。旧租约的迟到写回不能覆盖新租约，刷新阶段沿用绝对期限。将入口在途控制放在实际生产前，异步等待 Kafka 回调，避免持有房间锁或请求线程等待消费。收到 Broker 确认才返回 `202`，Redis 标记写回失败允许沿用这次已确认的结果。结果未知时复用原提交标识。以同步等待正式回执的 `200` 方式也能表达终态，但将消费者积压传回请求资源，因此采用已确定的 `202` 契约。 [接口和错误](../../../docs/design/room-messages/v2/api.md) · [Redis 预约](../../../docs/design/room-messages/v2/storage.md#账号额度和提交绑定)

### Kafka 裁决、恢复与回执

沿用设计中的提交、正式弹幕和回执三个 Topic，初始各 6 分区。提交与正式事件使用规范化后的 `roomId` 键。Kafka Streams 在同一分区内顺序处理提交，分别保存房间末序号、业务去重及预约终态。使用 `exactly_once_v2` 原子推进状态、输出事件和输入进度。重复、冲突和逾期命令按已有规则裁决，未正式接收的事件无法推动房间序号。状态清理器采用有界批次并遵守业务判重和预约有效期。Kafka Producer 幂等可处理传输重试，业务重复请求还需要这层裁决。 [消息队列设计](../../../docs/design/room-messages/v2/event-contract.md)

广播、历史和回执各自固定消费组，读取已提交事件。回执投影只在 Redis 写入不可变终态或终态超过查询期时确认处理进度。重建投影按 Kafka 回执记录恢复未到期的结果。GET 只从认证上下文组合账号、会话、房间和预约标识，避免泄露回执是否属于其他用户。响应 `unconfirmed` 归并缺失、投影延迟与窗口过期。 [回执投影](../../../docs/design/room-messages/v2/storage.md#回执投影)

### 历史事务、分页和保留

新增两张历史表，使用 MyBatis 和 Flyway 实现已确定的列和索引。历史消费按分区批量处理；以固定房间顺序锁定水位，校验新记录连续，相同事件允许重放。遇到冲突、跳号和不明确的事务结果时由消费方保留未确认位置。数据库事务提交后才能提交下一个连续 Kafka offset。清理侧使用相同水位锁，只删除达到保留期的房间连续前缀。读取使用主库一致性快照，固定补拉目标至 `throughSeq`，保留真实的 `storedThrough`。直接从 Redis 读取历史无法提供同样的可恢复范围，MySQL 同事务管理历史和水位。 [数据库设计](../../../docs/design/room-messages/v2/database.md)

### 房间广播和浏览器收敛

广播消费组按分区顺序发布 Redis。失败时有界退避并暂停受影响分区，确认之后才推进进度。已超过实时窗口的消息通过历史水位恢复。房间订阅使用引用计数和订阅代次，在订阅确认后先排入 `ready`。本机按房间串行入队，每连接独立写入，限制数量、字节和队列年龄。水位查询按活跃房间批读，只在水位前进时发送通知；Redis 重订阅后主动发出 `resync_required`。使用房间频道可以把消息只送到订阅该房间的实例；全局频道会让每个实例额外处理无本机观众的房间消息。 [房间频道和本机资源](../../../docs/design/room-messages/v2/storage.md#房间频道与订阅)

Vue 按房间和会话管理提交快照、回执轮询及有界消息缓冲。每次就绪后先缓冲实时消息，再读取最近历史或继续已知序号。以整数语义比较字符串序号，按连续水位去重追加。延迟或乱序事件通过历史补齐，窗口过期与缓冲耗尽均通过提示后重新建立基线恢复。沿用列表布局、最近 100 条、阅读位置及输入法交互。 [前端合并规则](../../../docs/design/room-messages/v2/api.md#前端合并与恢复)

## Risks / Trade-offs

- [生产确认后 Redis 写回或客户端响应丢失] → 原租约到期后允许重试，由 Kafka 判重恢复相同正式消息。区分入口拒绝和结果未知。
- [Redis 发布与 Kafka offset 提交之间退出] → 保留原事件 ID 和序号，重复发布时由页面合并。同房间发布和网关入队保持串行，旧订阅事件使用代次隔离。
- [历史消费慢于实时或停在故障分区] → 历史接口报告连续水位，补拉保留原游标。暂停并恢复受影响分区，保留期外无法恢复的水位保持关闭。
- [MySQL 历史通知、Kafka 确认和实时推送争用单机资源] → 各阶段设置独立有界并发，记录延迟、积压与下发量，使用固定流量基线评估。
- [Kafka 分区或序号状态未经迁移] → 首轮冻结分区规则，变更时按设计排空并迁移房间末序号与有效去重状态。

## Migration Plan

1. 创建历史表和三个业务 Topic，确认单 Broker 的事务日志、消费进度和状态 Topic 可用。保持新链路接入未就绪，直到状态恢复完成。
2. 暂停新发送并断开旧房间连接，协调切换前后端，重新获取 Ticket 后启用 V2。V2 发送仅走持久化途径。已运行的 V1 内存弹幕在其既有生命周期内处理。
3. 回退时暂停 V2 新发送，优先完成已确认提交的正式裁决、历史与回执追平，再切回 V1 前后端。保存 Kafka 数据、应用 ID、末序号及历史表，重新启用 V2 时从原位置继续。 [部署与运行](../../../docs/design/room-messages/v2/deployment-and-operations.md)
