## Context

LiveFlow 当前在 `AuthView.vue` 中建立会话，并根据 `App.vue` 传入的房间地址选择个人主页或房间页。Spring MVC 已提供房间创建、本人查询和详情。发送弹幕由 HTTP 受理，WebSocket 负责同房间下行广播。方案背景见 [变更提案](proposal.md)。

## Goals / Non-Goals

**Goals**

- 用现有 Maven 分层、登录状态和代理扩展房间浏览链路，避免重复鉴权与逐房间查询资料。
- 保持同毫秒的房间稳定翻页，让浏览、搜索、详情和广播遵守一致的显示名规则。
- 延续弹幕的原子受理、限流、去重和房间隔离；显示名查询和网络写入均在内存临界区外完成。

**Non-Goals**

- 视频流、房间开关播、成员持久化和历史弹幕属于后续阶段。范围见 [变更提案](proposal.md)。

## Decisions

### 房间 HTTP 与模块边界

`liveflow-api` 在现有 `RoomController` 增加列表 GET，并在 `SecurityConfiguration` 中显式将该路径列为需要认证，从已验证 JWT 的 `sub` 获取查看者。读取接口无 CSRF 请求头要求，创建和弹幕写请求继续经过现有安全过滤链。对查询参数保留原始多值信息，先拒绝未知键和重复键，再按显式规则解析 `q`、`limit`、`cursor`，以区分缺省和显式空值。列表与详情沿用房间 GET 的不可缓存响应和错误映射。详情的可见数据增加 `ownerName`。创建和本人查询继续复用原来的房间对象。

`liveflow-core` 在房间服务处理参数、规范化、游标和分页结果，在 Mapper 使用绑定参数执行只读查询。列表和详情从 `rooms` 关联 `users` 并左关联 `user_profiles`，以非空昵称优先，保留用户名的原拼写。列表直接计算 `isMine`，公开 DTO 仅输出对应契约的字段。票据和弹幕发送路径只需验证房间存在，使用共用的按 UUID 存在性查询，避免为了检查存在而反复读取房主资料。Redis 继续保存会话和 Ticket。 [房间接口](../../../../docs/design/room/api.md) · [房间数据库设计](../../../../docs/design/room/database.md)

前端使用公共 UUID 和标题定义共享字段，再分别定义创建与本人查询、详情和目录的响应类型。房主显示名只作为目录和详情的必填字段，避免现有调用误以为创建响应中也包含该字段。

### 搜索与游标

数据库增加 `idx_rooms_created_at_room_uuid (created_at DESC, room_uuid DESC)`。空关键词走浏览查询。非空关键词先复用单行字符规则与 Unicode 首尾空白清理，再转义 `!`、`%`、`_`，在两端添加 `%`，通过 `LIKE ... ESCAPE '!'` 和 `utf8mb4_0900_as_ci` 匹配。统一排序不依赖关键词相关度。现阶段单表的标题包含查询可复用房间数据，搜索服务或全文索引留到确有查询量需求时评估。 [列表 SQL](../../../../docs/design/room/database.md#列表查询与分页)

列表按 `(created_at, room_uuid)` 严格取游标之后的记录。房间子查询明确使用组合索引按 `limit + 1` 取数，外层只关联当页房主资料并重申排序。存在额外一条时以当前页最后一条生成游标。偏移量会因翻页期间插入新房间而漂移，排序键边界能让后续页继续沿用原位置。各页可见数据独立读取，新增较新的房间在重新读取首页时出现。

游标采用无填充 Base64URL，解码载荷为 `1:<UTC epochMillis>:<canonical UUID v4>:<normalized q UTF-8 SHA-256 hex>`，编码长度上限为 256。先检查编码和字段，再按 MySQL `DATETIME(3)` 的有效范围校验时间，以 UTC `LocalDateTime` 传入 SQL，并校验房间 UUID 和关键词摘要。游标只携带读取边界，不授予访问权限。格式或查询不匹配时使用既有 `INVALID_REQUEST`。前端清空游标后可按当前关键词回到首页。

### Vue 路由与列表状态

`App.vue` 从浏览器地址派生 `/`、`/profile`、`/rooms/{roomId}` 和现有 `/dev` 页面。应用内部通过浏览器 History API 切换地址，响应 `popstate`，复用同一个 `AuthView` 和 `useAuth` 实例。路由只决定登录成功后展示的页面，进入房间或个人主页时仍可原址恢复。导航链接提供真实 `href`，保留复制、刷新、新标签和直接访问；同标签的站内导航复用当前会话。继续使用现有 Vite 与应用入口回退规则。

目录区分输入草稿与 URL 已提交的关键词。提交、清空以及浏览器前进后退时，按地址重建首页和游标。页面以「会话、查询代次」识别在途请求；翻页另标记请求边界，重复点击只触发一次。同一个查询的成功结果按服务端顺序追加；旧代次、已离开页面或旧会话的结果均丢弃。首页错误保留输入和重试入口，后续页错误保留当前列表与游标。

目录点入观看页时，用当前浏览历史记录的 `state` 带入列表来源及已提交关键词。明确的「返回直播间列表」根据该值恢复首页，分享链接使用当前站点与房间路径。个人主页和直接访问的房间默认返回 `/`。查询词依附于列表入口，复制的房间链接只包含房间地址。

### 弹幕受理与房间主题

发送仍由 `RoomMessageController` 从可信身份获取账号。进入 `RoomMessageService` 后完成原有房间与正文检查，先在受理锁内判断有效的重复请求或冲突。新请求在锁外通过现有个人资料查询规则取显示名，再在锁内复查受理记录，处理资料查询期间已经获胜的并发请求。存在记录时按原结果裁决；资料缺失账号走会话失效，依赖异常通过弹幕错误映射返回服务不可用。没有受理的请求不消耗额度。只有在锁内通过复查与容量、额度检查后，才依次入队、写入受理记录和计入额度；实际网络写入由连接队列处理。 [状态裁决](../../../../docs/design/room-messages/storage.md#提交裁决与广播顺序)

广播事件携带一次读取确定的 `senderName`，由 `RoomSocketHandler` 随 `message` 编码。HTTP DTO、首帧和断线重连继续使用现有契约。客户端解析 `senderName` 并以纯文本渲染；时间在前端转为本地 24 小时制 `HH:mm:ss`，接收顺序保持为消息顺序。 [WebSocket 帧](../../../../docs/design/room-messages/api.md#websocket-接收协议)

深灰主题限定在房间观看页。桌面端 16:9 观看区旁为 320–380 px 弹幕列，窄屏垂直排列。弹幕区顶部提供独立连接状态，发送区固定在面板底部。消息区使用等宽时间列和可换行的发送者、正文区域，长连续文本允许断词。追加和裁剪前记录是否位于底部或首条仍可见的消息位置，更新后按相同状态恢复滚动，新消息提示仅在离开底部并有新消息时展示。 [房间布局](../../../../docs/design/room/design.md#房间页面框架) · [面板交互](../../../../docs/design/room-messages/design.md#弹幕面板)

## Risks / Trade-offs

- 标题包含匹配会扫描游标范围内的候选记录。以页大小上限和组合排序索引约束读取，并用实际数据查看执行计划。
- 显示名读取增加单次新提交的数据库访问。现有去重命中无需读取资料，查询放在受理锁外，查询故障按可重试错误处理。
- 当裁剪最早消息正好移除阅读位置时，保留仍存在的首个可见项作为锚点；全部移除时从当前保留列表顶部继续阅读。
- 发布期间新版 Vue 需要新的列表接口与显示名字段。先让提供新契约的后端接管相关 HTTP 和 WebSocket 流量，再切换 Vue 静态资源。

## Migration Plan

1. 新增 V7 之后的 Flyway 索引迁移，沿用现有房间记录与 UUID，确认已有库和空库均可执行。
2. 先发布后端，检查已登录列表、详情和两客户端弹幕帧，再发布新版 Vue。验证直达 `/profile` 与 `/rooms/{roomId}` 的前端入口回退，以及同源 HTTP 代理和 WebSocket 升级。
3. 回退时先恢复旧版 Vue，再按需回退后端。新增索引与已创建房间继续保留。
