# room-messages Specification

## Purpose

让 LiveFlow 已登录用户在同一直播间发送和实时接收纯文本弹幕，明确消息受理、短期去重、房间隔离和页面恢复的行为。

## Requirements

### Requirement: 房间接收连接鉴权

系统 MUST 提供 `POST /api/v1/rooms/{roomId}/ws-ticket`，校验 Bearer、CSRF、当前会话和房间 UUID，成功返回不可缓存的 `200`、`ticket` 和 `expiresIn`。票据绑定账号、会话及房间，默认 30 秒有效且只可消费一次。`/ws/rooms` MUST 校验来源，默认在 5 秒内接收首帧 `auth`。验证票据与当前会话且房间接收路径就绪后 MUST 先发送 `ready` 再发送房间消息。就绪连接 MUST 周期复查原会话，默认每 15 秒一次。无法确认会话时关闭连接。

#### Scenario: 有效票据建立连接

- **WHEN** 已登录用户为存在的房间申请票据，并从允许来源在首帧提交
- **THEN** 服务端在房间接收路径就绪后以绑定的 UUID 返回 `ready`，该连接可以接收对应房间的后续消息

#### Scenario: 拒绝无效鉴权和重复消费

- **WHEN** 来源未获允许、首帧无效或超时、票据过期，或两个连接并发消费同一票据
- **THEN** 无效请求无法入房，并发消费最多一个连接取得资格

#### Scenario: 登录会话被替换或无法确认

- **WHEN** 连接建立后会话在其他浏览器被替换，或复查遇到认证存储故障
- **THEN** 旧会话的 HTTP 发送按认证契约拒绝，旧连接在复查确认失效或无法确认时关闭

### Requirement: 发送弹幕及短期去重

系统 MUST 提供 `POST /api/v1/rooms/{roomId}/messages`。写请求要求有效 Bearer、CSRF 和存在的房间，JSON 正文只接受标准小写 UUID v4 的 `clientMessageId` 和字符串 `content`。原始正文拒绝控制字符、行段分隔符和未配对代理项，去除首尾 Unicode 空白后为 1–100 个码点。确认提交已持久化入队后，系统 MUST 返回不可缓存的 `202`、`Location` 和 `{submissionId,status,retryUntil,receiptExpiresAt}`，其中状态为 `queued`。重试与回执查询期限自首次入队许可分别为 10 和 30 分钟，未曾正式接收的命令首次处理晚于许可后 12 分钟时拒绝。写入结果无法确认时 MUST 返回 `503 MESSAGE_SUBMISSION_UNKNOWN`，客户端使用原标识和正文重试。

系统 MUST 按账号共享滚动额度，默认 10 秒准许 5 个新提交，覆盖不同标签页和房间。重复请求沿用既有绑定和额度。按会话、房间 UUID 和客户端标识判重，约定重试窗口内相同规范化正文最多产生一个正式事件，复用原 `messageId`、`roomSeq` 和 `sentAt`。相同标识绑定异文时，已知冲突返回 `409 MESSAGE_ID_CONFLICT`；进入异步处理的冲突通过拒绝回执报告。新提交必须从认证账号获得显示名。账号不存在时按会话失效处理，资料查询故障返回 `503 ROOM_MESSAGES_UNAVAILABLE`，授权入队前的这一失败不记入额度。

#### Scenario: 接受有效提交

- **WHEN** 有效会话在现有房间提交合法正文且账号额度充足
- **THEN** 获得持久化入队确认后返回 `202` 及回执地址；正式接收时唯一的消息 UUID 和房间序号可由回执查询

#### Scenario: 并发重试和正文冲突

- **WHEN** 重试窗口内并发提交相同标识和正文，或已有标识再次携带不同的规范化正文
- **THEN** 相同提交复用原正式结果，正常预约存续期间只占一次额度；已知内容冲突返回 `409`，异步发现的冲突由回执报告，均不生成额外正式事件

#### Scenario: 账号共享发送额度

- **WHEN** 同账号通过多标签页或不同房间达到了当前发送额度
- **THEN** 新提交返回 `429 MESSAGE_RATE_LIMITED` 和整数秒 `Retry-After`，未进入正式接收

#### Scenario: 拒绝无效或无法受理的请求

- **WHEN** 请求输入、认证或 CSRF 无效，房间不存在，或依赖故障使本次调用在生产前停止
- **THEN** 按约定返回相应的 `400`、认证错误、`404` 或 `503 ROOM_MESSAGES_UNAVAILABLE`，本次调用未提交消息

#### Scenario: 资料读取故障时查询已受理提交

- **WHEN** 原预约已确认入队且仍可查，同一会话在资料存储故障期间重复提交原标识和正文
- **THEN** 服务端返回原预约信息，已有正式结果仍可查询，本次不再次计入额度

#### Scenario: 未知确认后重试

- **WHEN** 首次请求写入后响应丢失，用户在允许窗口内以原标识和正文重试
- **THEN** 最终只形成一条正式事件，取得的正式回执指向同一消息及房间序号

### Requirement: 本机同房间实时分发

系统 MUST 为每个房间从 1 开始按正式受理顺序分配递增 `roomSeq`，同一提交的重试不产生新序号。在线消息 MUST 按房间限制可见范围，公开 `message` 帧包含 `roomSeq`、`messageId`、`senderName`、`content` 和 `sentAt`。公开房间序号和水位统一使用十进制字符串表示。各接收方读取同一正式消息的数据，显示名采用已认证发送者首次许可时的昵称或原拼写用户名快照。下行公开帧隐藏账号 ID。实时分发可能在订阅中断时漏发或在恢复时重复，接收端以正式消息和房间序号合并。慢连接达到资源限制时单独关闭。订阅恢复时系统 MUST 发出 `resync_required`，向活跃房间通知增加的历史水位 `history_progress`。

#### Scenario: 同房间分发和跨房间隔离

- **WHEN** A 和 B 已就绪且同处一间房，C 在另一间房，A 发送一条正式接收的消息
- **THEN** A 和 B 在正常连接下看到相同的序号、显示名及正文，C 收不到该消息

#### Scenario: 慢连接隔离

- **WHEN** 某连接持续阻塞并达到队列条数、字节、排队时间或写入限制
- **THEN** 服务端关闭该连接，同房间其他正常连接继续接收

#### Scenario: 发送者修改昵称后再次发送

- **WHEN** 用户发送消息，保存新昵称，然后发起另一条新提交
- **THEN** 新创建的预约使用新显示名，已有正式消息及原提交重试继续使用原快照

#### Scenario: 分发重放

- **WHEN** 正式消息实时发布后广播进度未确认，恢复后重复发布该事件
- **THEN** 重复帧保留原 `messageId` 与 `roomSeq`，浏览器只显示一条

### Requirement: 房间弹幕面板与恢复

房间页 MUST 提供连接状态、正文输入、发送按钮、发送反馈和独立滚动列表，发送区固定在面板底部。在收到当前房间的 `ready` 后才允许发送。页面 MUST 区分排队、最终接收、拒绝与结果未确认，按回执更新发送状态，按历史与实时消息更新列表。初次进入读取最近历史，重连复用同一房间及会话的最近连续游标。页面 MUST 合并同步期间的实时缓冲与历史，按房间序号连续追加并去重。列表最多保留最近 100 条。有空间时在同一行显示浏览器本地 `HH:mm:ss`、发送者和纯文本正文，空间不足时自然换行。输入法组字期间避免误发送。切换房间或会话时清理旧列表、提交、补拉与连接任务。

#### Scenario: 广播早于发送响应

- **WHEN** 用户先收到实时消息，再取得 `202` 或正式接收回执
- **THEN** 列表只增加一项，响应和回执只更新该次提交状态

#### Scenario: 发送结果不明确

- **WHEN** 请求超时、响应丢失或回执暂不可见
- **THEN** 页面保留原正文和标识，提示状态待确认；窗口内手动重试复用标识，重连不会自动发送

#### Scenario: 重连、刷新与换房

- **WHEN** 用户断线重连、刷新页面或切换房间与会话
- **THEN** 同页同会话重连申请新票据并从已连续处理位置补拉，保留列表和草稿；刷新时按首次进房读取最近历史，切换时隔离旧回调和旧房间数据

#### Scenario: 消息在阅读和跟随时到达

- **WHEN** 新消息在列表底部跟随或用户上翻阅读时到达
- **THEN** 底部跟随继续，向上阅读时保持仍可见条目的位置并提示「查看新消息」

#### Scenario: 历史与实时交错或漏收末尾事件

- **WHEN** 先收到缺口后的实时事件，或在订阅中断期间漏掉末尾事件且之后没有新弹幕
- **THEN** 页面暂存超前事件，按连续游标补拉并去重；订阅恢复或历史水位推进驱动补拉，恢复窗口内的末尾消息也可找回

#### Scenario: 补拉范围或缓冲已耗尽

- **WHEN** 历史范围已清理，或等待中的实时缓冲达到容量上限
- **THEN** 页面提示重新同步并读取最近历史窗口，按新的连续起点继续展示

### Requirement: 查询本人当前会话的发送回执

系统 MUST 提供 `GET /api/v1/rooms/{roomId}/messages/submissions/{submissionId}`，要求有效 Bearer 与当前会话，仅可读取调用者在对应房间和当前会话内的回执。响应为不可缓存的 `200`，包含 `submissionId` 与 `status`。正式接收时 MUST 返回 `accepted`、`messageId`、`roomSeq` 与带三位毫秒的 UTC `sentAt`。终态拒绝时 MUST 返回 `rejected` 与 `MESSAGE_ID_CONFLICT` 或 `MESSAGE_SUBMISSION_EXPIRED`。暂未可查、已超出查询期及其他作用域的有效格式标识 MUST 返回相同形状的 `unconfirmed`；查询依赖失败返回 `503 ROOM_MESSAGES_UNAVAILABLE`。同一提交的可见终态及原有回执字段在查询期内保持一致。

#### Scenario: 入队结果和正式接收分开确认

- **WHEN** 请求取得 `202`，用户在正式回执形成前后分别查询
- **THEN** 回执尚不可查时返回 `unconfirmed`，正式接收后返回 `accepted`，其消息标识、房间序号和时间与正式弹幕一致

#### Scenario: 迟到提交与异文冲突

- **WHEN** 已入队提交在可查询期内首次被处理时已超过接收期限，或其客户端标识已正式接收过不同规范化正文
- **THEN** 相应预约可查询到拒绝码，已正式接收的原弹幕及回执保持有效

#### Scenario: 其他房间、账号或会话查询回执

- **WHEN** 已登录用户使用不属于当前作用域的合法提交标识查询
- **THEN** 响应为 `unconfirmed`，未透露其他提交的存在、内容或最终状态

### Requirement: 历史持久化与有序查询

系统 MUST 保存正式接收的弹幕及每房间的连续落库进度。重复处理同一正式事件时 MUST 保持历史只存在一条对应记录及其原字段。发生事件冲突或不可恢复的历史缺口时 MUST 暂停受影响的历史推进。系统 MUST 提供经 Bearer 和当前会话鉴权的 `GET /api/v1/rooms/{roomId}/messages`。默认读取最近一页；传入 `afterSeq` 时读取严格大于该序号且不超过 `throughSeq` 和连续落库水位的范围。`limit` 缺省为 100，允许 1–100。省略 `throughSeq` 时取 `max(afterSeq, storedThrough)`；只有提供 `afterSeq` 时才可传入 `throughSeq`，且后者不得更小。响应 MUST 包含按 `roomSeq` 升序的 `items`、`earliestSeq`、`storedThrough`、`targetThrough` 与 `nextAfterSeq`。历史不可用返回 `503 ROOM_MESSAGES_UNAVAILABLE`。游标落在清理范围之前时返回 `409 ROOM_HISTORY_GAP` 及当前可读范围。

#### Scenario: 首次查询最近历史

- **WHEN** 已登录用户查询存在房间的历史且未传游标
- **THEN** 按房间序号升序返回该房间最近一页，水位为本次读取时已连续落库的最大序号，公开字段与实时弹幕一致

#### Scenario: 落库尚未达到补拉目标

- **WHEN** 客户端按游标补拉，但历史存储仅写到目标的一部分
- **THEN** 系统返回当前连续可读范围和原查询目标，客户端可从最后已读序号继续查询

#### Scenario: 历史批次重复消费

- **WHEN** 历史批次已提交，但处理进度未确认，重启后再次收到同一事件
- **THEN** 对应消息仍只有一条且内容保持原值，连续水位不回退

#### Scenario: 历史保留范围已越过客户端游标

- **WHEN** 请求的 `afterSeq` 小于最早可读序号减 1
- **THEN** 系统返回 `409 ROOM_HISTORY_GAP` 和水位，客户端可以重新读取最近历史
