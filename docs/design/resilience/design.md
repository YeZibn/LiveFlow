# 单实例限流设计

本稿定义独立限流模块的目标契约。认证限流归独立模块管理，沿用登录与注册固定窗口。弹幕使用每账号两次新预约至少间隔 10 秒的冷却策略。范围为一个 LiveFlow 进程中的登录、注册和弹幕提交。 [认证设计](../auth/design.md) · [弹幕 V2 设计](../room-messages/v2/design.md)

## 技术选型与职责

沿用 Java 21、Spring Boot MVC、Spring Data Redis、Redis Lua、MySQL、Kafka 和 Vue。固定窗口依靠 Redis 计数与 TTL，弹幕依靠账号冷却键与提交预约。三个入口均通过 Lua 完成需要原子裁决的读写。限流作为现有 Maven 子模块内的独立业务边界。 [Maven 父 POM](../../../backend/pom.xml) · [本地依赖定义](../../../compose.yaml) · [前端依赖定义](../../../frontend/package.json)

| 层 | 职责 |
| --- | --- |
| `liveflow-core` | `resilience` 定义规则及认证限流接口。认证服务显式调用限流接口，`AuthSessionStore` 负责会话读写。弹幕服务继续通过提交预约接口取得许可。 |
| `liveflow-infrastructure` | `resilience` 实现认证 Redis 限流，在同一 Lua 调用内处理计数和到期。弹幕适配器使用统一配置的冷却时长，在预约脚本内完成冷却与预约裁决。 |
| `liveflow-api` | 校验适用的认证、CSRF 与请求字段，使用服务端可信来源和账号标识，将业务拒绝转换为 HTTP 响应。 |
| Vue | 读取服务端等待提示，保留草稿与原提交状态。 |

## 业务规则

| 策略 | 主体与算法 | 默认值与计数点 |
| --- | --- | --- |
| 登录 | 原样账号名和可信连接来源 IP，分别使用固定窗口 | 60 秒内账号 10 次、来源 60 次。请求字段有效后、密码校验前共同计数。 |
| 注册 | 可信连接来源 IP，使用独立固定窗口 | 600 秒内 10 次。请求字段有效后、计算密码哈希前计数。 |
| 弹幕 | 当前认证账号 ID，使用冷却键。各房间、标签页和登录会话共享 | 两次新预约至少间隔 10 秒，在首次创建预约时开始冷却。 |

## 端到端流程

登录先校验字段。脚本对账号及来源两个维度一起判定，全部通过才递增。账号名保留原拼写。注册脚本只使用注册额度；格式合法的重复注册依然计入尝试，账号唯一性由 MySQL 裁决。 [认证数据库](../auth/database.md)

弹幕先通过现有鉴权与输入检查。已确认入队的同标识同正文可以快速返回原 `202`。对其余提交，在 Redis 预约脚本内先裁决已有预约，再检查新请求的账号冷却。冷却结束才创建新预约并交给既有 Kafka 流程。首次许可在 `12:00:00.250` 时，下一次新许可最早为 `12:00:10.250`。这个间隔约束预约获准时刻，Kafka 确认、异步处理和重试仍会影响观众看到弹幕的时间。 [弹幕 V2 接收流程](../room-messages/v2/design.md)

同标识同正文沿用原预约和租约，重试不延长冷却。同标识异文返回既有冲突。新预约获得许可后，即使 Kafka 写入失败或结果未知，也沿用该冷却期限；同一标识仍可按原协议重试。限流拒绝不创建预约，也不刷新冷却。
