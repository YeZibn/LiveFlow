# 房间存在性缓存

## 范围与数据归属

MySQL 的 `rooms` 是房间是否存在的权威来源。缓存 Redis 保存按 UUID 查询的派生布尔值。应用在通过现有鉴权和 UUID 校验后，通过 `RoomService.exists()` 读取该值。Ticket 签发、WebSocket 兑票、新弹幕发送和历史查询共用这一入口。房间详情、列表、本人房间、发送者资料和历史快照继续由各自的读取路径提供。 [房间设计](design.md#房间存在性缓存) · [MySQL 查询](database.md#按-uuid-检查房间存在性) · [弹幕接口](../room-messages/v2/api.md#房间存在性判定)

缓存使用独立 Redis。三台应用连接同一缓存实例，各自保护本机发起的 MySQL 回源。会话、Ticket、冷却、提交预约、回执、广播和后台租约仍由现有 Redis 提供。两套 Redis 分别配置客户端连接和容量。 [部署与运行](deployment-and-operations.md)

## Key 和生命周期

| Key | Redis 类型与值 | 生命周期 |
| --- | --- | --- |
| `<env>:liveflow:room:exists:v1:{<roomId>}:value` | String。ASCII `1` 表示存在，`0` 表示 MySQL 确认不存在。 | `1` 每次写入在 4–6 分钟内取随机 TTL。`0` 在 4–6 秒内取随机 TTL，截止时间从取得此次回填租约时起算。 |
| `<env>:liveflow:room:exists:v1:{<roomId>}:fill` | String。本次持有者的随机令牌。 | 取得即开始计时，初始租约 5 秒，成功回填、明确失败或创建后预热时按下文规则释放。 |

`<env>` 是同一部署环境三台应用共享的缓存命名空间，`<roomId>` 是标准小写 UUID v4，外层花括号是 Redis 哈希标签。例如，`local:liveflow:room:exists:v1:{aee115e4-3589-4db0-a5ad-3e2406a6001b}:value`。同一 UUID 的两个 Key 在同一哈希槽。所有生命周期参数为联调初值。读取命中保留原有到期时间。Key 缺失表示当前没有可用缓存值。遇到非预期的值类型或编码时，记录缓存异常，并按缓存不可用处理。

短期负缓存吸收同一不存在 UUID 的重复查询。不同 UUID 各自需要独立确认，实际回源量由应用预算控制。正缓存分散到期，冷启动和集中丢失由同一预算控制。

## 读取和跨实例回填

1. 读取 `:value`。命中 `1` 时继续业务，命中 `0` 时按房间不存在处理。未命中时，同实例同 UUID 的请求可在等待预算内复用本机在途回填。
2. 本机执行者通过 Lua 二次读取 `:value`。仍缺失时对 `:fill` 执行 `SET NX PX`。取得租约时，同一脚本用 Redis 时钟记录开始时间并返回。请求在获得回源额度后，对主库执行一次现有的存在性查询。
3. 租约被占用的请求错峰复查 `:value`，复查间隔在 20–40 毫秒内取值。等待和复查 Redis 的命令耗时共用 150 毫秒预算。预算内读到值就继续，超时或复查失败时返回暂不可用。等待者在当次请求内结束，不另起 MySQL 查询。后续请求可在租约到期后接手。
4. MySQL 查询成功后，通过 Lua 校验当前 `:fill` 仍等于本次令牌，原子写入 `:value` 并释放租约。写负缓存时使用按租约开始时间计算的绝对截止，截止已过时只释放租约。MySQL 明确失败、请求取消或额度不足时，由持有者按令牌尝试释放。释放无法确认时由租约到期兜底。
5. 命令超时、缓存淘汰或实例退出可能导致租约丢失。已失去租约的请求可以使用自己成功读取的 MySQL 结果完成当次响应，回填脚本须拒绝它的写入和解锁。回填错误同样保留已取得的 MySQL 结果，后续请求可重新读取。MySQL 的失败结果永远不写为 `0`。 [Redis SET 命令](https://redis.io/docs/latest/commands/set/) · [Redis 租约与令牌校验](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

正常情况下，同一冷 UUID 由一个实例完成回填。租约失效或被淘汰时允许发生重叠查询，由下述全路径预算限制数据库负载。

## 创建、预热和可见性

创建房间在 MySQL 事务内插入并回读。事务确认提交后，为最终创建成功的 UUID 执行一次缓存预热。Lua 先写 `1` 并设置正缓存 TTL，再删除该 UUID 的回填租约。读取到旧快照的回填者随后校验令牌时会失败。事务回滚、唯一约束冲突或事务结果未确认时，创建路径不写缓存。 [创建事务](database.md#创建)

预热失败时，创建接口仍以已提交的 MySQL 结果返回 `201`，并记录失败供观测。若 Redis 中已有负缓存，或者提交前已启动的查询稍后尝试写负缓存，负缓存仍须在其原截止前失效。由于负缓存截止从回填租约开始时间起算，由本次创建造成的缓存陈旧窗口最长为负 TTL 上限，按初值为 6 秒。本人房间和房间详情继续从 MySQL 读取已提交结果。 [创建接口](api.md#创建房间)

当前房间生命周期以创建为主。引入房间删除时，删除流程需在对外开放前定义提交后失效和旧回填隔离规则。

## 缓存故障与回源预算

初次读取或租约竞争发现缓存 Redis 不可用，或部署设置为旁路时，进入本机受控回源。同一实例上正在查询同一 UUID 的请求共用在途结果，查询结果产生后清理本机记录。跨实例各自执行预算，认证仍由业务 Redis 校验。

普通未命中、缓存故障、旁路和缓存恢复初期，发起实际 MySQL 存在性查询的执行者共用同一个实例级预算。命中和复用在途结果无需额外额度。

| 预算 | 联调初值 | 执行规则 |
| --- | --- | --- |
| 回源速率 | 每实例持续 30 次/秒，突发额度 6 | 令牌桶按实际启动的回源尝试扣令牌。无需排队等待额度。 |
| 在途查询 | 每实例最多 4 条 | 取得许可后再申请连接和发出 SQL。查询实际结束或确认取消后归还许可。上层请求提前退出时，仍在执行的查询继续计入在途。 |
| 三台合计 | 持续 90 次/秒，突发额度合计 18，最多 12 条在途 | 按全部实例预算相加估算。扩容或改变配置时重算。 |

预算耗尽时返回暂不可用。MySQL 查询失败按依赖故障传播。房间不存在只来自成功查询或已有确认的负缓存。房间存在性额度独立于账号发送冷却、发送者资料读取、房间详情以及历史快照内的其他 SQL。 [弹幕错误映射](../room-messages/v2/api.md#房间存在性判定)

## 基线与对照场景

2026-11-25 在提交 `4c0572f` 上，以同机三应用、单 MySQL、单 Redis 和单 Broker 运行 2,340 次测试请求。主要请求档为三台合计 60 并发，每组 300 次，均分到各应用实例。按 MySQL 查询日志统计实际执行的 SQL。

| 场景 | 现有行为 | 改造后的验收目标 |
| --- | --- | --- |
| Ticket 查询同一个不存在 UUID | 300 次存在性 SQL，300 次 `404`。 | 从冷 Key 开始，在同一负缓存有效期内只执行一次 SQL，三台均返回 `404`。该场景使用正常且能在等待预算内完成的 MySQL。 |
| Ticket 查询 300 个不同的不存在 UUID | 300 次存在性 SQL，300 次 `404`。 | 回源受速率及在途上限约束。获准且查无房间返回 `404`，额度拒绝返回 `503`。 |
| Ticket 查询热门 UUID | 300 次存在性 SQL。 | 到期后的并发回填正常时只执行一次 SQL。热缓存读取阶段执行 0 次 SQL。另测租约到期接管和旧持有者迟到。 |
| 历史查询热门 UUID | 300 次请求执行 1,200 条 SQL，其中 300 条为存在性查询。 | 热缓存阶段省去存在性查询。继续核对历史阻断、水位和消息页。 |
| 房间详情和发送冷却 | 300 次详情查询执行 300 条 SQL。冷却内 60 次发送均返回 `429`，各执行 60 次房间查询和发送者资料查询。 | 详情保留作对照。发送热缓存消除存在性查询，资料与冷却裁决保持现有逻辑。 |
| 仅停新增缓存 Redis | 基线停的是业务 Redis，120 次请求在鉴权阶段返回 `503`。 | 业务 Redis 继续可用。新增缓存 Redis 停止期间原会话仍有效，实际房间存在性回源量受预算约束。恢复后命中率回升，回源量下降。 |

另用固定 UUID 构造创建与旧回填并发，覆盖提交后预热成功、预热故障、事务回滚和负缓存接近截止等路径。分别统计正命中、负命中、SQL 及 HTTP 响应。 [联调与观测](deployment-and-operations.md#联调与观测)
